Architecture cible

Beaucoup de trafic en lecture (infos publiques) avec de gros pics pendant le Giron, plus une partie transactionnelle (comptes, billetterie, paiements). Principe clé : séparer le public très cacheable du transactionnel.

BriqueChoixPourquoi
FrameworkNext.js (App Router)Statique/ISR pour la vitrine (absorbe les pics via cache) + dynamique dans un seul projet. Excellent SEO.

ORMPrismaSchéma typé, migrations propres, lisible pour l'équipe.

Plan de fondation

On construit dès le départ pour accueillir la plateforme complète, mais on met en ligne par étapes — le public d'abord, le transactionnel ensuite.

Étapes de la fondation (avant toute fonctionnalité)

1️⃣
Structure Git propreBranches main (stable) + develop + branches de feature
2️⃣
Fichiers de base.gitignore, README, .env.example (aucun secret réel)
3️⃣
Squelette Next.jsArborescence + config, sans logique métier
4️⃣
DockerDockerfile + docker-compose (app + PostgreSQL)
5️⃣
Cible InfomaniakDécider hébergement (managé vs VPS Docker)

Découpage par phases (mise en ligne progressive)

Phase 1  Fondation

Repo propre, squelette, Docker, CI, branches. Base technique en place.

Phase 2  Vitrine publique

Programme, accès, cantines, sponsors, contact. 100 % cacheable → en ligne rapidement, absorbe les pics.

Phase 3  Comptes & espace comité

Authentification, rôles, espace bénévoles / comité.

Phase 4  Inscriptions / billetterie

Paiements Stripe + TWINT, sécurisés et séparés de la vitrine.

Phase 5  Back-office admin

Gestion des contenus, inscriptions, exports pour le comité.

Décisions à prendre avec toi avant de lancer la Phase 1 : confirmer la stack (Next.js + PostgreSQL + Stripe/TWINT + Docker), et le type d'hébergement Infomaniak (managé ou VPS).

Règles Git & sécurité

Les garde-fous du projet — non négociables pour garder une base stable et sûre.

🌿 Git

🟢
main toujours stableReprésente une version qui marche. Jamais de grosse fonctionnalité codée directement dessus.
🌿
Une branche par fonctionnalitéOn développe à part, on teste, on relit le diff, puis on propose le merge.
🔍
Relecture avant mergeVérifier les changements, détecter régressions et incohérences avant de valider.
Cycle type d'une modification importante
1. Vérifier l'état du projet → 2. Créer/utiliser une branche dédiée → 3. Développement par Claude Code → 4. Tester → 5. Examiner les diffs → 6. Corriger → 7. Proposer le merge vers main
